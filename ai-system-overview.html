AI Organization System / 2026.07.08

AIを一人の天才ではなく、
引き継げる組織として動かす。

Codex、Claude Code、Cline / DeepSeek、OpenClawを、共通ルール・仕事票・検証・記録でつなぐAI連携システム。その理念、現在動いている仕組み、残る課題、次の戦略を一つにまとめます。

01
Why

なぜ「AI組織」が必要なのか

AI単体に抽象的な指示を与えるだけでは、品質がぶれ、引き継げず、改善が蓄積されない。理念の正本：Google Docs「AI組織 設計指針」
↻

モデルは変わる

価格・性能・利用上限が変化する。特定AIだけに依存すると、交代時に仕事が止まる。

≠

得意不得意が違う

設計、実装、長文理解、外部サービス、QCで向くAIが異なる。役割分担が必要。

＋

ミスを資産にする

失敗を責任追及で終わらせず、原因・対策・再検証を組織へ戻す。

02
Constitution

設計を支える8つの原則

01

個人能力より組織能力

設計・実行・検収・記録を一つのAIへ集中させない。

02

AIを交換可能にする

記憶ではなく、仕事票・標準形式・成果物を正本にする。

03

引き継ぎ可能な記録

CURRENT、LOG、仕事票で途中交代しても再開できる。

04

証拠で品質保証

完成報告ではなく、実ファイル・テスト・読み戻しで判定。

05

実行とQCを分離

重要作業は別AIまたは機械検証で独立確認する。

06

ミスを改善資産へ

記録だけで終わらせず、対策の効果確認まで追う。

07

必要なときに必要な情報だけ読む

目的・対象・完了条件を先に示し、長文資料は段階的に読む。

08

人間が方向性と重大判断を握る

本番変更、公開、外部送信、費用、安全、優先順位は人が承認する。

ローカル運用版：company/ai-operations/PRINCIPLES.md

05
Task lifecycle

会話ではなく、仕事票が仕事を運ぶ

01 REQUEST人間の依頼自然な言葉、目的、困りごと
02 PLAN具体化・分割対象、禁止事項、完了条件、担当AI
03 DISPATCHactiveへ投入Dispatcherが担当AIを起動・案内
04 EXECUTE限定実行ロック取得、指定範囲だけを処理
05 VERIFY証拠＋独立QCテスト、実在、差分、読み戻し
06 LEARN記録・改善LOG、CURRENT、BUGS、INCIDENTS

状態は「成功／失敗」の二択ではない

needs-ai → in-progress → qc-pending → done。曖昧なら needs-human、修正が必要なら needs-fix、続行不能なら blocked。安全に止まることも正常な成果です。

Rules & memory

AI Rulesは、組織の共通OS

AI-RULES.md

全AI共通ルール。作業前のCURRENT確認、ロック、技術別バグ知識、終了時のLOG→CURRENT更新を定義。

P

PRINCIPLES.md

次のAIが5分以内に再開するための現在地。完了履歴は置かない。

LOG.md

何をしたか、なぜしたか、気づきを残す時系列の履歴。

BUGS / INCIDENTS

症状、原因、修正、再発防止。責任追及ではなく仕組み改善。

10
Continuity

トークン切れでも、仕事を止めない

1. 作業前 対象CURRENTと仕事票を読み、ロックを取得する。
2. 作業中 成果物、判断、テストをファイルへ残す。会話だけに置かない。
3. 中断時 次のAIはCURRENT・仕事票・差分から再開する。モデル固有の記憶を前提にしない。
4. 完了時 LOG追記 → CURRENT更新 → 仕事票状態 → ロック解除の順で閉じる。
5. 実例 Codexの上限やClaudeの利用上限が発生しても、別AIがQC・記録・次工程を引き継いだ。
会話は消える。ファイルに残した判断と証拠が、AI組織の記憶になる。

Quality strategy

DeepSeekを「安いAI」から狭く強い実行者へ

観測された傾向

  • 長文の重要条件を見落とす
  • 曖昧な指示を推測で補う
  • 失敗でも完成報告する
  • Cline / OpenClaw両経路で類似

新しい投入基準

  • 1目的・1成果物
  • 編集1〜3ファイル
  • 初期入力3ファイル以内
  • 必須条件7項目以内

完了ゲート

  • 曖昧ならneeds-human
  • 未達ならneeds-fix
  • 証拠なし完成は禁止
  • 最終QCは別AI

DeepSeek → DeepSeek委任

許可するが深度1まで。parent_task_id、委任者、経路、QC担当を記録し、子から孫への再委任と自己QCを禁止。

評価指標

API単価ではなく、初回QC合格率、修正回数、QC時間、人間対応を含む「検収合格1件あたりの総コスト」で判断する。

13
Gaps

次に解くべき課題

優先度 高

記録されたミスが改善へ閉じていない

事故は残るが、タグ、再発回数、対策状態、次回見直し日、効果確認が統合されていない。

優先度 高

全体ポータルの鮮度が現場より遅い

OpenClawやDashboardは進化した一方、AI OperationsのBOARDや古い説明が追いつかないことがある。

優先度 中

Dashboardが「現在」しか見せない

過去の仕事票、修正履歴、QC連鎖、成果物を案件単位で検索できない。

優先度 中

Dashboardから依頼できない

人間が仕事票形式やスクリプトを覚える必要がある。安全なdraft作成UIが欲しい。

運用課題

active / locksの意味が濁る

invalid、qc-pending、released履歴が残り、「今やる仕事」だけを示す台帳になっていない。

品質課題

接続正常と仕事の正しさが混在

ONLINEでも、成果物欠落、状態矛盾、古いCURRENTは起こり得る。HEALTHYという意味判定が必要。

14
Roadmap

これからの方針

Phase 1 / Now品質と正本を整えるDeepSeek短票の実運用、active整理、全体CURRENT同期、MEMORY反映確認。
Phase 2ミスを改善キューへ事故タグ、重大度、再発、対策状態、週次「直すべき3件」を生成。
Phase 3履歴Dashboardactive / review / done / Issue / NAS / LOGをTask IDで検索・連結。
Phase 4安全な依頼UIDashboardでdraft仕事票作成→人間確認→active投入。直接実行は後段。

最終的に目指す状態

人間は「何を達成したいか」を伝える。調整AIが具体的な仕事へ分割し、適切なAIへ割り当て、システムが成果を検証する。失敗はタグ付き改善キューへ戻り、次の仕事票とルールが少しずつ良くなる。

15
Conclusion

仕組みは、かなり動き始めている。
次は、学ぶ組織にする。

記録して引き継ぐ仕組みはできた。これからは、記録を優先順位付きの改善へ変え、過去と現在を一つの画面で見て、人間がもっと簡単に仕事を頼めるようにする。

交換可能

AIが変わっても仕事を続けられる。

検証可能

完成報告ではなく証拠で判断する。

改善可能

失敗が次のルールと仕事票を良くする。
