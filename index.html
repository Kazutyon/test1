理念・設計原則

機能より先に、どういう組織を作るかを決める。

理念の正本はGoogle Docs「AI組織 設計指針」。ローカル運用版は company/ai-operations/PRINCIPLES.md です。

中心命題

AIは「優秀な一人」を作るのではなく、「協力できる組織」を作る。

特定モデルの記憶に依存せず、役割・記録・検証・改善を仕組みに持たせます。

判断順序

  1. 安全に停止できる
  2. 正本と証拠が残る
  3. 別AIが引き継げる
  4. ミスを改善へ戻せる
  5. 速度・自動化率・単価
新システム設計時の必須確認
  • AIごとの役割が分かれている
  • 担当AIを交換できる
  • 途中から引き継ぐ正本がある
  • 完了を証明する検証がある
  • 実行とQCが分離されている
  • ミスの記録先と見直し周期がある
  • 人間の承認点とrollbackがある

ローカル仕事フロー

AI Team QueueからCodex / Claude / Clineへ渡る経路。

1. 仕事票作成TASK v2またはDeepSeek短票
2. active投入status=needs-ai
3. guardduplicate / stale / lock
4. 担当起動Claude自動、Codex/Cline半自動
5. QC・done結果記録、ロック解除
担当ID起動方式自動度注意
claudeclaude CLI非対話高利用上限時のretry-pendingは未完成
codexVS Codeで仕事票を開き起動文をコピー半自動人間がセッションへ渡す
deepseekCline経路。選択モデルは固定しない半自動ルーティングIDであり実モデル名ではない
Dispatcher guard仕様
  • 重複判定：Task ID、対象パス＋tags、対象パス＋タイトル、目的＋タイトル
  • needs-ai 72時間更新なし → blocked
  • in-progress 24時間更新なし → blocked
  • done移動済みタスクのstale lockを自動修復
  • needs-ai 以外の票は起動しない
6

メインPC → OpenClaw送信フロー

OpenClawへ依頼するときは通常のactive仕事票を使わない。

1. 正規投入New-OpenClawTask.ps1
2. Issue仮作成route:openclaw
3. NAS tasktask-N.md + rules + contract
4. worker v4HMAC、allowlist、tool loop
5. 検収required paths → done

Task IDと保存先

# Issue #68 の場合 task_id = "task-68" task_input = "openclaw-inbox/task-68.md" task_output = "openclaw-outbox/task-68/" required_base = "result.md" html-create = ["result.md", "index.html"]
完了条件：Issueへ done が付いても、必須成果物が存在し内容検証を通るまで「検収済み完了」ではありません。
v4 contractが制限するもの

Task ID、Issue番号、操作種別、期待成果物、許可root、実行制限、署名を固定します。秘密鍵はNAS・Issue・ログへ出しません。immutable release、backup、rollback、flagで段階配備します。

7

OpenClaw → メインPC受信フロー

外部から来た仕事は、activeへ直行させずreviewを検疫地点にする。

1. Discord / OpenClaw依頼受付
2. GitHub IssueメインPC停止中も保持
3. Bridgereview仕事票へ変換
4. 安全判定auto-active / needs-human / danger
5. Dispatcher担当AIへ渡す
OpenClawは司令塔ではなく外部サービス担当です。自分で agent:openclaw Issueを作り、自己完結処理することは禁止されています。

状態主条件意味

主要データ契約

Dashboardとworkerが共有する最小限の構造。

heartbeat.json — 機能生存
{ "schema_version": 1, "generated_at": "ISO-8601", "host": "openclaw-linux", "worker_status": "active", "current_task_id": "task-68 | null", "last_success_at": "ISO-8601 | null", "last_error_code": null }

systemdはプロセス生存、heartbeatは処理ループの機能生存。別々に観測します。

execution-summary.json — Task単位の実行証跡
{ "task_id": "task-68", "issue_number": 68, "status": "success | failed", "attempts": 1, "result_path": "openclaw-outbox/task-68/result.md", "validation": "passed | failed", "error_code": null }

失敗時も保存。秘密情報、例外全文、絶対ローカルパスは禁止。

dashboard-state.json — UIが読む唯一の統合JSON

collectorが30秒周期でatomic生成。sources.worker/github/nas/ai_team_queue を個別に持ち、各sourceは ok / stale / error / unknown。UIはGitHubやNASへ直接接続しません。

ai-team-snapshot.json — メインPCのキュー要約

件数、担当AI、状態、最終更新だけをNASへ送信。仕事票本文、機密度、ローカル絶対パス、ユーザー情報を含めません。現在は20分周期のWindowsタスクで更新します。

ルール階層と読み込み順

長文を全部読むのではなく、上位原則から必要な範囲へ降りる。

Google Doc: AI組織 設計指針（理念の正本） └─ company/ai-operations/PRINCIPLES.md（設計判断） └─ AI-RULES.md（ワークスペース共通実行ルール） ├─ 対象プロジェクト CURRENT.md / README.md ├─ docs/bugs/{technology}.md ├─ docs/ai-role-patterns/*.md └─ 仕事票（目的・対象・完了条件） OpenClaw: AI-RULESの短縮運用版 → rules/common.md（50行以内） ＋ rules/kinds/{Kind}.md ＋ rules/projects/{Project}.md → NAS同期 → OpenClaw MEMORY.md
二重正本防止：理念の意味変更はGoogle Docを先に更新。ローカルPRINCIPLESは実務用要約、OpenClaw commonは50行以内の実行用短縮版です。

DeepSeek追加規約

  • 原則1目的、1成果物、編集1〜3ファイル、初期入力3ファイル、必須条件7項目以内
  • 曖昧なら needs-human、未達なら needs-fix
  • DeepSeek→DeepSeek委任は深度1まで。親Task IDと委任者を保持し、自己QC禁止

セキュリティ境界

完全自動化より、限定権限・検疫・rollbackを優先。

ネットワーク

LAN＋Tailscale限定

DashboardはLANとtailnet内のみ。Tailscale Funnel、ルーターポート開放、一般公開は禁止。

秘密

表示・成果物へ出さない

GitHub token、HMAC鍵、env本文をNAS、Issue、Discord、HTML、JSON、ログへ保存しない。

限定root

OpenClawの保存先はTask配下へ限定。..、絶対パス、ドライブ文字を拒否。

人間承認

本番、外部送信、公開、削除、課金、権限変更は明示承認。

復旧

backup、manifest、SHA、immutable release、flag、段階Gateでrollback可能にする。

メインPCの D:\vs_code をOpenClawへ直接書き込ませない。GitHubとNASを検疫・受け渡し境界として維持します。

日常運用手順

どの場面で何を確認するか。

ローカルAIへ仕事を渡す
  1. 対象プロジェクトのCURRENTを確認
  2. 仕事を1成果物単位へ分割
  3. 仕事票に目的・対象・禁止事項・完了条件を書く
  4. ACTIVE-LOCKSを確認
  5. activeへ置く
  6. Dispatcher検知後、担当経路で実行
  7. QC後にdone、LOG/CURRENT更新、ロック解除
OpenClawへ仕事を渡す
  1. New-OpenClawTask.ps1 をメインPCで使う
  2. Project / Kind / Description / Expected Artifactsを指定
  3. GitHub IssueとNAS task、contract生成を確認
  4. worker処理後、Issue状態とNAS必須成果物を独立確認
  5. doneでも成果物欠落なら完了扱いしない
OpenClawルールを同期する
  1. rules/common.md が50行以内か確認
  2. メインPCで Sync-OpenClawRules.ps1 実行
  3. FTP 226とversionを確認
  4. 通知Issueを確認
  5. OpenClaw側MEMORY.mdへの反映を確認

2026-07-08の同期：version 20260708-001、Issue #68。

Dashboardを見る
  1. overall状態を確認
  2. source別状態と最終成功時刻を確認
  3. 異常なら元のGitHub / NAS / heartbeat / snapshotへ戻る
  4. ONLINEでも成果物・CURRENT整合は別途確認する

症状から正本へ戻る最短経路。

症状最初に確認次に確認典型原因
Dashboard UNKNOWNcollector.generated_at時計、systemd、JSON parsecollector停止、時計ずれ
worker DEGRADEDheartbeat ageGitHub/NAS/Queue sourceheartbeat遅延、source stale
Issue doneだが成果物なしNAS task-N配下required_paths、worker commentSAVE不足、検証バグ
仕事票が動かないstatus=needs-aiかDispatcher log、担当AI、duplicateqc-pending/invalid、重複、起動経路
ロックが残るACTIVE-LOCKS仕事票done移動終了処理漏れ
DeepSeekが完成を誤報完了条件別証拠実ファイル、テスト、独立QC指示過長、曖昧、自己検収

復旧原則：推測で状態を直さない。元のIssue・成果物・仕事票・ログを読み、どこまで成功したかを確定してから再投入します。

用語集

このシステム内での意味。

正本
矛盾時に最終的に信用する情報源。
Task ID
仕事を横断追跡する識別子。OpenClawでは通常 task-{Issue番号}。
Kind
OpenClawタスク種別。種別ごとにルールと必須成果物が異なる。
QC
Quality Control。実行担当とは別の検収。
CURRENT
現在地、未完了、次の一手を持つ再開入口。
LOG
完了履歴、判断、検証を持つ時系列記録。
heartbeat
workerの処理ループが機能していることを示す時刻付きデータ。
snapshot
メインPC側Queueの安全な要約。本文や秘密情報を含めない。
HMAC contract
Taskと許可操作を署名で固定するv4の実行契約。
fail-closed
不明・未検証なら成功扱いせず停止する設計。
readback
保存後に別経路で読み戻し、内容一致を確認すること。
一致する章がありません。別のキーワードを試してください。
AI Organization Integrated Specification — 説明・把握用の統合資料。最新運用状態は各CURRENT.mdを優先してください。
